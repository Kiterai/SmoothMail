# フォルダ情報エラー：同名LIST項目の重複

## 提供ログから確定したこと

- `op=3`ではIMAP認証が成功し、フォルダ一覧として16項目を受け取っています。
- 4244行目の`folder-metadata-invalid`は、`duplicate_count=1`、`first_duplicate_index=16`、`duplicate_of_index=2`です。空名と負の未読数はともに0です。
- 本文取得を進めた後、保存段階でこの重複を拒否し、ロールバックして同期が失敗しています。正常終了の記録もあり、クラッシュではありません。

直接の原因は、SmoothMailが同じ名前のフォルダ記述を重複したまま蓄積し、保存側が一意な一覧を要求しているのに、受信側で統合していなかったことです。認証失敗やSQLite破損が原因だったという証拠はありません。

ログにはフォルダ名・応答原文を保存しないため、サーバが同じ名前を複数回返したのか、KIMAPによるデコード・INBOX表記の正規化後に同名になったのかは断定できません。サーバやKIMAPそのものの不具合とまでは主張しません。

## 修正

LIST受信中に、同じ名前・同じ階層区切りの記述を1フォルダへ統合します。複数回の通知に分かれていても同じように扱い、STATUS・フォルダごとの取得処理を重複させません。取得前と最後の整合性確認のSELECT／EXAMINEは維持します。保留フォルダ操作後の一覧再取得にも適用します。保存側の検証は緩和しません。

- 名前の独自の大文字小文字変換やUnicode正規化は行いません。INBOX以外の`Archive`と`archive`は別項目のままです。
- 属性は大文字小文字を区別せず統合します。選択可能な記述が1つでもあれば、階層用`\NoSelect`項目で隠しません。すべてが`\NoSelect`なら選択しません。
- `\HasChildren`があるときは、矛盾する`\HasNoChildren`・`\Noinferiors`を除きます。他の属性は保持します。
- 同名でも階層区切りが異なる場合は、誤ったフォルダ操作を避けるため、勝手に統合せず取得前に明確なエラーで停止します。
- 元のLIST応答数10000件の上限、空名・負の未読数などの保存検証、本文取得のバッチ上限は維持します。

診断には`sync-list-raw-total`、`sync-list-duplicates-merged`、最初の重複項目／元項目番号、統合後の`sync-list-complete`を記録します。フォルダ名・サーバ応答・認証情報は記録しません。

## 検証

提供ログと同じ「16番目が2番目と同名」を合成サーバで再現し、15フォルダへ統合する試験を追加しました。同一通知内／通知を跨ぐ重複、属性差、INBOX表記の正規化、大小文字で異なる一般フォルダ、階層区切りの矛盾、応答数上限、保留フォルダ操作後の再取得も検査します。

最終結果はSandbox12実行ファイルで181件成功・失敗0、ホスト15対象・Python31件も成功です。`build/local-run`は修正版へ更新済みです。

実アカウントへの接続、DB削除・書換え、メールや資格情報の取得は行っていません。利用者環境での修正後の再取得確認は別途必要です。

回帰試験では、全項目が`\NoSelect`の場合に「選択フォルダなし」をSQL NULLとして保存しようとする別の不具合も見つかりました。この内部表現を空文字列へ統一し、選択不可のフォルダへ無理に接続せず、一覧情報だけを保存できるように修正しました。提供ログの失敗原因はこの別件ではなく、上記の同名重複です。
