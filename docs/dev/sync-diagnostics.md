# 同期時の異常終了診断

## 2026-11-13の強化

再発ログのCRTブレークポイントを受け、CRTアサート/Qt Fatalの固定分類と、最大40フレームのモジュール名・相対コード位置、スレッドID、起動EXEのSHA-256を追加しました。アサート本文やメモリダンプは保存しません。CRT/Qt Fatalは記録後に異常終了し、無視して処理を継続しません。非ASCIIヘッダによるKMimeの再現済み不具合を修正しましたが、利用者の実事象の原因確定とは区別します。調査結果と検証は`crash-investigation-20261113.md`を参照してください。

**大量メール対策の更新:** 通常アプリの全件メモリ保持と1万件/128 MiB上限は、分割取得・ディスク退避・100件のSQLページ表示へ置き換えました。現行動作は`large-mailboxes.md`を参照してください。以下の原因調査は、分割対応前の強制終了報告に対する調査記録です。原因を再現確定したという意味ではありません。

## 保存先と内容

通常アプリは`QStandardPaths::AppLocalDataLocation/diagnostics`へセッションごとの診断を保存します。Windowsでは通常`%LOCALAPPDATA%\SmoothMail\SmoothMail\diagnostics`です。起動ランタイムのフォルダではなく、ユーザーデータの保存先です。

- `日時-UUID.log`: UTC日時、アプリ/Qt/ビルド情報、IMAP認証・LIST・STATUS・SELECT・ヘッダ取得・本文取得・MIME解析・キャッシュ保存・画面反映の段階、件数/バイト数、KJobの数値エラーコード。処理段階ごとにflushします。
- `日時-UUID.fatal.txt`: Windows未処理例外コード、命令アドレス、取得できる場合のモジュール名と相対オフセット。C++の`std::terminate`は固定文言で記録します。事前に開いたWindowsハンドルへ、Qtやヒープ割当・ロックを使わずにベストエフォートで書き込みます。
- `日時-UUID.active`: 正常終了前のセッションマーカー。正常なワーカー終了後に削除します。次回起動時、該当プロセスが既に存在しなければ`.active.abnormal`へ変更します。別の起動中プロセスのマーカーは変更しません。

ログにはメールアドレス、サーバ名、フォルダ名、件名、本文、添付、サーバ応答、例外メッセージ、認証情報を保存しません。プロセスメモリを含むダンプも自動作成しません。1セッションの通常ログは4 MiBで折り返します。過去セッションは自動削除しないため、調査に必要なログを保管した後、不要分は手動で削除できます。

ログ保存先を作成できない場合は起動時にエラーを表示し、診断が有効なふりをして起動しません。通常起動用cmdのOAuth読込方式は変更していません。

## 保証できないこと

`TerminateProcess`、タスクマネージャーでの強制停止、OS停止、電源断、fail-fast、スタック/ヒープの重大破損では、例外ハンドラーが呼ばれない/書込みできない場合があります。その場合、残った最終段階と次回起動時の未正常終了マーカーが手掛かりです。マーカーのみでは「クラッシュ」と「外部からの停止」を区別できません。PID再利用やプロセス参照権限の制約で検出を保留する場合もあります。Qt初期化前の障害、ログ保存先のディスク障害も保証範囲外です。ログは完全なスタックトレースではありません。

## 現時点の原因候補（利用者の事象は未再現）

1. **メモリ不足**: 従来は選択フォルダの全ヘッダ・全本文・解析結果を保持し、他の閲覧済みフォルダもUIに保持していました。64 MiBの単体メール上限だけでは、メールボックス全体の使用量は制限できません。C++割当失敗やライブラリ側の大きな一時領域が候補です。今回、1フォルダ10000件、1同期の原文合計128 MiB、フォルダ10000個/階層64段の安全上限を追加し、上限到達時は既存表示/キャッシュを置換せず失敗として表示します。保存済みキャッシュの初期復元も1アカウント10000件/原文128 MiBを超える場合は止めます。これはプロセス全体のメモリ上限ではなく、複数アカウント/フォルダの累積やデコード時の膨張まで解決するものではありません。根本的には差分同期・オンデマンド本文取得が必要です。
2. **特殊/破損MIME、深い入れ子**: `MimeParser`の構造上限検査はKMimeの`parse()`後です。また受信時にKIMAP自身もKMimeを利用します。従って異常な構造が依存ライブラリの解析でスタック枯渇・アサート・メモリ破損を起こす可能性は、この後段チェックだけでは除けません。今回これが原因だったという再現結果はありません。
3. **ジョブ/ワーカー終了と切断・タイムアウトの競合**: KIMAP/KSMTPのジョブ、ネストしたイベントループ、終了中のセッション破棄を確認すべき候補です。KIMAPにはジョブ破棄時のキュー除去処理があるため、スタック上のジョブというだけでuse-after-freeとは断定できません。通信失敗の通常経路は合成サーバーテストで確認していますが、全競合条件の不存在は証明していません。
4. **依存DLL/Qt/OS側の障害、外部からの終了**: 例外コードとモジュール相対位置があれば絞り込めます。受領済みの報告には障害モジュール、例外コード、問題メール、件数の情報がなく、特定できていません。以前修正したKJobのquit-lockによる終了と今回の事象が同一だという証拠もありません。

再発時は、同時刻の`.log`、`.fatal.txt`、`.active.abnormal`と、操作していた段階・概算件数/サイズを確認します。実メールや秘密情報を共有する必要はありません。シンボル照合用に、利用したEXEとPDBの組合せを保持してください。

## 検証

`tst_diagnostics`は正常終了、子プロセスの強制停止→次回起動での検出をテストします。Windows例外と`std::terminate`の意図的な異常終了は`SMOOTHMAIL_GUI_SANDBOX_TEST=1`の使い捨てguest内だけで実行します。利用者の実同期クラッシュを再現したテストではありません。
