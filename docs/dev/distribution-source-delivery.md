# 同一配布ページでの対応ソース提供

`spec/distribution.md`の方針に従い、Qtはオープンソース条件で使用し、対応ソースはバイナリのダウンロードと同じページで別途配布します。商用契約の選択や未履行の書面オファーを前提にしません。

## 準備用コマンド

```bat
cmake -P cmake/FetchQtLegalSources.cmake
cmake -DOUTPUT=build/source-windows-review -P cmake/PrepareWindowsSourceReview.cmake
```

Qt取得は既存SDKのSBOMに記録されたqtbase/qtsvgの固定commitを対象とします。SDKの構築・インストール・入替えはしません。Gitの対話的な認証は使わず、既存ソースの変更や別commitへの強制切替は拒否します。

ソース収集はcleanな追跡ソースからtarを作り、`.git`・個人設定・キャッシュ・実メール・資格情報・ビルドreceiptを含めません。SmoothMailのスナップショットにはビルドスクリプト・パッチ・ライセンス・テストを含めます。KDE等は固定原本、GNU/SASLはハッシュ照合した原本アーカイブを提供し、SmoothMail/vcpkgの適用パッチと手順を併せて再構築できる形でレビューします。

`source-manifest.review.json`はアーカイブごとのcommit/SHA256と欠けたQtソースを記録します。Qt未取得でも他のソース収集は進めますが、不足を隠して完成品としません。gitlinkがあるソースは未解決のsubmoduleを黙って落とさず停止します。

**これらは準備・レビュー用です。生成されたという理由だけで、完全な対応ソースの提供完了とは扱いません。**

## 公開前の照合

1. 配布バイナリの情報ダイアログのcommitと、同時公開するSmoothMailソースのcommitを一致させる。dirty/不明な識別子は配布ビルドで拒否する。
2. 各依存の版・commit・適用パッチ・構築条件と、実際に同梱したDLLを照合する。Git原本とパッチだけの集合で再構築手順が欠けないことを確認する。
3. Qtの固定原本・内蔵第三者コード・必要な構築入力を確認する。SDKの原本commitが分かっただけでは、対応ソースを受領者へ提供したことにならない。
4. ソースアーカイブを別フォルダへ展開し、内容とSHA256、パッチ適用・必要な再構築・ライブラリ差替えを検証する。
5. 実際の配布ページに、対応する版のバイナリ・ソース・SHA256・通知への導線を並べる。ソースを別の時期に公開する前提で先にバイナリを出さない。

実ページの公開先は未設定です。ローカルでの準備は進められますが、最終公開時には実際にソースを取得できることを確認する必要があります。Qt等のオープンソース条件は、それぞれの著作権・通知・改変/差替え等の条件を維持して適用します。

## 情報ダイアログ

「ヘルプ→このソフトウェアについて...」にソフト名・版、ビルド日とソースcommit、コンポーネント別の原文・変更通知を表示します。左で項目を選び、右でプレインテキストとして閲覧します。外部サイトへ自動接続しません。

`SMOOTHMAIL_LEGAL_DIR`にライセンス資料を指定すると構築時に埋め込みます。開発用の`manifest.review.json`は監査未完了を明記し、配布ビルドでは拒否します。最終配布では、ZIPのlegalと情報ダイアログの入力に同じ承認済み`manifest.json`を使います。
