# DIST-04: 限定パッチの保守性・ライセンス検討

2026-11-14。検討のみ。パッチは作成・採用・適用していない。

## 技術上の選択

| 方式 | 保守性 | 主な影響 |
|---|---|---|
| Windows向けにcheckUpdateを明示的に無効化 | 局所化しやすい | 公開関数を残しても設定移行の意味は失われる。将来の呼出しを検知する必要がある |
| helperを再配置可能にする | 中程度 | 移行機能を維持できるが、helper/スクリプトの同梱・探索・安全性・追加ライセンス監査が必要 |
| KConfig等の静的化 | 比較的大きい | DLL間共有状態、依存構築、未使用除去、再リンク条件の検証範囲が広がる |

現在のSmoothMailでは設定移行をKConfigに委ねていないので、最初の案が製品の必要機能に対して最小。ただし上流互換の完全なKConfigを提供する案ではない。

### 無効化案の条件

- `KConfig::checkUpdate(const QString &, const QString &)`のシグネチャ・exportを維持する。削除してABIを破壊しない。
- 無効時は外部プロセスを起動せず、設定を書換えず、移行済みの記録も捏造しない。戻り値がvoidなので、固定文言の警告等で機能がないことを検知可能にする。引数や設定内容を診断へ出さない。
- 上流側の既定は有効を維持する明示optionが、将来の上流提案には適する。SmoothMailのWindows Debug/Releaseでは同じ選択を使う。名称・仕様は未決定。
- 不要なパス定義を無効時に生成しないようにする。helperのビルド/インストール除外は、ターゲット参照やビルド時利用を確認した上で別途扱う。
- 将来依存がこのAPIを使うようになった場合は無効化の前提を再評価する。ソース検索だけでなくimport/生成物と合成回帰も確認する。

### 既存保護への組込み

- 固定commit・原本分離・`git apply --check`の既存機構を再利用する。KConfigを第6の変更対象として明示する。
- 変更patchとKConfig DLL/Qt/構成を結ぶreceiptを生成し、`ValidateMailDependencies.cmake`の検証対象へ追加する。現行対象一覧にはKConfigはない。
- 調整を黙って自動適用するfuzzや失敗の無視をしない。上流更新時は適用成功だけでなく仕様/呼出し元を再確認する。
- helperを起動しないこと、設定を変更しないこと、export維持、通常KConfig利用、既存メール回帰、実DLLの個人パス検査を試験する。設定を扱う合成試験はQtのテストモード/使い捨て領域で実施する。
- 上流が修正したら互換性確認後にローカルパッチを削除できるよう、適用範囲・目的・撤去条件をREADMEへ記載する。

## ライセンス上の確認

直接確認した原文:

- KConfig `src/core/kconfig.cpp:1-8`、`kconfig.h:1-9`: LGPL-2.0-or-later。
- 同梱`LICENSES/LGPL-2.0-or-later.txt`: 改変と変更日表示（2節）、ライブラリのバイナリ配布と対応ソース（4節）、利用プログラムと再リンク等（5/6節）。
- これは当該ファイルの確認であり、KConfig全体・ビルド用CMakeファイル・推移依存の全監査ではない。ライセンス選択を勝手にLGPL 3等へ統一しない。

ライブラリを改変すること自体は許諾される。機能を削ったというだけでアプリ独自コードのMITを変更したり、ライブラリをMIT化したりするものではない。一方、変更したLGPLライブラリとその変更は、適用されるLGPL条件を満たして配布する必要がある。

出荷前に必要な整備:

1. 元の著作権/SPDX/ライセンス原文を保持し、変更ファイルへ変更の事実と日付を明示する。READMEや第三者通知だけで原文の変更表示要件を済ませない。
2. 非標準ビルドであり、設定移行機能が無効であることを`THIRD_PARTY_NOTICES.md`・patch README・製品legalへ明記する。
3. **配布DLLに対応する変更済みライブラリの完全なソースと必要なビルド/インストールスクリプト**を提供できるようにする。パッチ数行や動く上流URLだけの公開を、義務充足として扱わない。固定原本+差分+手順を保管し、実務上は対応ソースアーカイブを同等に取得できる形にするのが分かりやすい。
4. 対応するライセンス条件に沿った利用者の改変/再リンク・ライブラリ差替え等を妨げない。DLL方式だけで全義務が完了するとは扱わない。receiptは出荷ビルドの取り違え防止用で、利用者の改変DLLの実行禁止には転用しない。
5. 新たにhelper等を同梱する場合は、そのコード・スクリプト・ライセンスも別途監査する。無効化で同梱しないなら配布対象を増やさずに済む。

既にLGPL依存とローカルパッチを配布する前提があるため、追加されるのは主に「KConfigを変更済み依存として管理し、その対応ソース・通知・検証を追加する」作業。義務がゼロになるわけではないが、静的化より既存の配布設計を維持しやすい。

最終的な許諾条件の組合せ・配布方法の適否はDIST-02の実配布監査で確認する。本検討は法的充足の保証ではない。
