実装時の設計・検証記録です。ページ件数やDB版などは当時の値です。現在の操作手順は[利用方法](../../docs/usage.md)、残る制約は[未完了仕様](../../spec/inprogress/implementation-limits.md)を参照してください。

## 通常アプリの同期経路

- 全件同期のヘッダは連番100件ずつ、差分取得は日付検索したUIDを100件ずつ取得し、その結果のUIDで必要な本文を取得します。本文要求も最大100件、サーバが通知したサイズの合計が通常8 MiB以内になるよう分割します。8 MiBより大きいメールは単独で要求し、従来の1通64 MiB上限は維持します。受信バッチの実サイズも検査します。
- SQLiteワーカーのディスク退避用TEMPテーブルへ、最大100件/通常原文8 MiB単位で保存します。メールワーカーは保存完了を待つため、未保存バッチが無制限にキューへ積まれません。同期全体の件数/原文合計による1万件・128 MiB制限は、通常アプリの経路から撤去しました。
- UIDVALIDITYとUIDが一致するキャッシュは本文を再取得せず、今回のフラグとともに退避先へコピーします。初回は全件取得、以降は未取得の本文だけを取得します。
- 最後に再EXAMINEしてUIDVALIDITY、件数、UIDNEXTを照合し、退避先の件数・UID重複も検査します。連番ウィンドウがEXPUNGEなどでずれた可能性があれば公開せず、再試行を案内します。UIDNEXTを取得できないサーバでは安全のため分割同期を失敗とします。
- フォルダの取得成功後に、SQLiteトランザクションで公開キャッシュを置換します。失敗したフォルダの未公開ステージは破棄し、旧キャッシュを維持します。既に成功した別フォルダやフラグ再取得は保存されます。保留フラグは同期時に再送しますが、メール送信や削除の自動再実行はしません。大きいデータの公開中はDBへのページ要求が待つことがありますが、GUIスレッドではコピーしません。

この方式はメモリ使用をフォルダ全件の本文量から切り離しますが、全件キャッシュと退避先・ジャーナルのための**ディスク空き容量**は必要です。初回同期の通信量も全件分あります。極端に大きい1通や、依存ライブラリのMIME解析内部の問題を解決したという意味ではありません。受信相手がサイズを偽る場合のライブラリ内の一時割当まで厳密な上限を保証するものではありません。

既存の一括snapshot APIは小さい手動プローブ/互換テスト用で、従来の安全上限を維持します。通常ApplicationControllerは必ずSQLiteへの分割同期を使用します。

## メール一覧と本文

- 100件を1ページとして、件数範囲・総件数・ページ番号・総ページ数を表示します。0件は`0 - 0 / 0件`、総ページ数は1扱いで入力を無効にします。端数ページと件数減少時のページ番号補正に対応します。
- SQLiteに本文を含まない一覧用要約と検索用テキストを保存します。GUIへ渡す一覧は常に最大100件です。本文は選択した1通だけをワーカーで解析し、古い選択への遅延応答は破棄します。「自動で既読を付ける」がオンの場合は選択時に既読化を保留します。
- 文字列は「検索」ボタン/Enterで適用します。件名・差出人名/アドレス・宛先・テキスト本文（HTMLはソース）を対象とした、Unicode case folding後のリテラル部分一致です。添付のバイナリ内容は検索しません。SQLワイルドカードとして解釈しません。
- 重要/未読条件はチェック変更で適用し、文字列とのAND条件です。条件変更とソート変更は1ページ目へ戻します。**フォルダ全体を絞込/ソートしてからLIMIT/OFFSETでページ取得**します。日時など同値の場合はUIDで順序を安定させます。
- 検索中は不定進捗バーを表示し、GUIは操作可能です。新しい要求が来た場合は古いページ結果を無視します。既存キャッシュの要約を補完する際も1通ずつ解析し、新しい要求/終了を確認します。大きいSQL検索の途中停止まで保証するものではありません。
- スレッドはページ内の最大100件に対して構築します。ページ外の親は複製せず、そのページではルート表示になります。したがって100件の上限をスレッド展開で越えません。
- ダウンロード履歴からの元メール移動はフィルタを解除し、UID/UIDVALIDITYの位置からページを求めて選択します。
- 重要/未読バッジのクリックはローカルへ即時反映して保留し、同期時にUIDVALIDITYを検証してUID STOREの`+FLAGS`/`-FLAGS`でまとめて送信します。FLAGS再取得後はサーバ値を優先し、同期中に加えた新しい編集は次回へ残します。

## キャッシュ互換性

SQLiteのuser_versionは4です。v1/v2/v3の原文は削除せず、索引・保留フラグ・保留フォルダ操作等のテーブルを追加します。v1原文の要約は必要なフォルダのページ要求時にワーカーで順次補完します。通常起動時に全フォルダの本文をメモリへ復元しません。旧バイナリはv4を拒否するため、戻す場合は別途バックアップしたDBを使用してください。取得中の操作と接続先変更時の扱いは`inflight-operations.md`を参照してください。
