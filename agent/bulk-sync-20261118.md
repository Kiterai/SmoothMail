# 大量取得の高速化（2026-11-18）

- 基準ソースは`0de7e2c`。推定残り時間の既存変更は維持する。
- 従来の30フォルダ試験は大部分が空であり、今回の多数中規模フォルダの根拠にしない。
- 新しい`--bulk-only`は単一20000×2KiB、単一2000×64KiB、
  20フォルダ各500×2KiB。全条件で応答待ち20ms、3反復。
  初回／キャッシュ全件／差分不変／各フォルダ10追加／選択差分を独立記録する。
  実WANではなく模擬サーバーのコマンド応答待ちである。
- 現行版の計測EXEを`build/bulk-opt/baseline`に保存し、
  外部通信無効Sandboxで測定。DBをフォルダ別に検査するvalidatorを追加。
- 最初の改善はヘッダ窓100→1000（表示/DBページは100のまま）と、
  本文の受信→解析/DBステージを1消費者・最大1先行バッチで重ねるパイプライン。
  本文は8MiB目標、最大1000件、受信64MiB安全上限を維持。
  futureは正常/失敗/取消すべてでstage破棄前にjoinする。
  同時DB writerは増やさない。取消flagと診断Operationを消費者へ引き継ぐ。

## フォルダ数が多い場合

- 複数フォルダを更新する場合に認証後CAPABILITYを取得し、LIST-STATUS対応時は
  LIST RETURN (STATUS (UNSEEN))で未読数を一括取得する。
- 一部フォルダのSTATUSがなければそのフォルダだけ従来STATUS。
  明示拒否は通常LISTに一度だけ戻り、部分的な一覧は破棄する。
  非対応、対応、一部欠落、明示拒否の4試験を追加した。
- フォルダのSELECT／最終EXAMINEは省かない。フォルダ同士の同時公開は行わない。
  接続数増加によるサーバー制限や、account単位のステージの競合を避ける。

## 検証途中の記録

- 最初の全体回帰はtransport47件成功。GUIの子フォルダ作成1件が失敗した。
  この実行中に調査用Win+Rを送ったためフォーカス干渉の可能性があり、
  失敗を無視せず`output/regression`へ保存。次はguest入力を一切行わず再実行する。
- 後続バッチのMIME構造上限超過でも、先行1000件のステージが公開されないこと、
  修正後の再試行で1001件が揃うことを検査するtransport試験も追加した。
- ホスト非通信CTest14対象成功、Python52件成功（既存条件の8 skip）。

## DBステージの繰返し準備を削減

- raw挿入・索引挿入・再利用参照削除の3つのSQLを100件バッチごとに一度だけprepareし、
  bind/execを繰り返す。従来はメール1件ごとに3回prepareしていた。
- 索引JSONと検索文字列の生成を共通関数へ分離し、保存内容を変えない。
  バッチ途中の識別エラー／SQLエラーでは従来通りバッチ全体をrollbackする。
- ホストrepository全試験成功。最終版全体回帰と性能比較へ組み込んで確認する。

## 計測上の注意

- 多数フォルダの`flag_searches`は従来プローブの「UID SEARCH総数−1」では不正確なため、
  候補検索の本数（フォルダ数、選択更新では1）を引くよう修正した。
  修正前に回収したJSONのこの派生フィールドを多フォルダの根拠には使わず、
  元の`commands`の実測値から読み取る。同期時間・取得件数・DB検証には影響しない。
- 基準版/新版とも同じSandbox、同じ固定メール原文・応答待ち・フォルダ構成。
  LIST-STATUS非対応同士を主比較とし、対応時の追加測定は分ける。
