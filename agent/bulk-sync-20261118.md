# 大量取得の高速化（2026-11-18）

- 基準ソースは`0de7e2c`。推定残り時間の既存変更は維持する。
- 従来の30フォルダ試験は大部分が空であり、今回の多数中規模フォルダの根拠にしない。
- 新しい`--bulk-only`は単一20000×2KiB、単一2000×64KiB、
  20フォルダ各500×2KiB。全条件で応答待ち20ms、3反復。
  初回／キャッシュ全件／差分不変／各フォルダ10追加／選択差分を独立記録する。
  実WANではなく模擬サーバーのコマンド応答待ちである。
- 現行版の計測EXEを`build/bulk-opt/baseline`に保存し、
  外部通信無効Sandboxで測定。DBをフォルダ別に検査するvalidatorを追加。
- 最初の改善はヘッダ窓100→1000（表示/DBページは100のまま）と、
  本文の受信→解析/DBステージを1消費者・最大1先行バッチで重ねるパイプライン。
  本文は8MiB目標、最大1000件、受信64MiB安全上限を維持。
  futureは正常/失敗/取消すべてでstage破棄前にjoinする。
  同時DB writerは増やさない。取消flagと診断Operationを消費者へ引き継ぐ。

## フォルダ数が多い場合

- 複数フォルダを更新する場合に認証後CAPABILITYを取得し、LIST-STATUS対応時は
  LIST RETURN (STATUS (UNSEEN))で未読数を一括取得する。
- 一部フォルダのSTATUSがなければそのフォルダだけ従来STATUS。
  明示拒否は通常LISTに一度だけ戻り、部分的な一覧は破棄する。
  非対応、対応、一部欠落、明示拒否の4試験を追加した。
- フォルダのSELECT／最終EXAMINEは省かない。フォルダ同士の同時公開は行わない。
  接続数増加によるサーバー制限や、account単位のステージの競合を避ける。

## 検証途中の記録

- 最初の全体回帰はtransport47件成功。GUIの子フォルダ作成1件が失敗した。
  この実行中に調査用Win+Rを送ったためフォーカス干渉の可能性があり、
  失敗を無視せず`output/regression`へ保存。次はguest入力を一切行わず再実行する。
- 後続バッチのMIME構造上限超過でも、先行1000件のステージが公開されないこと、
  修正後の再試行で1001件が揃うことを検査するtransport試験も追加した。
- ホスト非通信CTest14対象成功、Python52件成功（既存条件の8 skip）。

## DBステージの繰返し準備を削減

- raw挿入・索引挿入・再利用参照削除の3つのSQLを100件バッチごとに一度だけprepareし、
  bind/execを繰り返す。従来はメール1件ごとに3回prepareしていた。
- 索引JSONと検索文字列の生成を共通関数へ分離し、保存内容を変えない。
  バッチ途中の識別エラー／SQLエラーでは従来通りバッチ全体をrollbackする。
- ホストrepository全試験成功。最終版全体回帰と性能比較へ組み込んで確認する。

## 計測上の注意

- guest入力を行わない再試験でも同じ子フォルダ試験が失敗した。
  contextAction helperは折り畳まれた「フォルダ」配下のmodel indexにも
  visualRectの中心をそのまま使っており、非表示行の空rectから別行を右クリックしていた。
  helperで祖先展開・scrollToを行い、indexAtが要求indexと一致することを追加検証する。
  製品のフォルダ処理・期待結果を変更せず、実際に表示した行を操作する試験に修正した。
  干渉なし失敗の全17EXEは285 passed / 1 failed / 0 skipped、`output/final-regression`へ保持。

- 多数フォルダの`flag_searches`は従来プローブの「UID SEARCH総数−1」では不正確なため、
  候補検索の本数（フォルダ数、選択更新では1）を引くよう修正した。
  修正前に回収したJSONのこの派生フィールドを多フォルダの根拠には使わず、
  元の`commands`の実測値から読み取る。同期時間・取得件数・DB検証には影響しない。
- 基準版/新版とも同じSandbox、同じ固定メール原文・応答待ち・フォルダ構成。
  LIST-STATUS非対応同士を主比較とし、対応時の追加測定は分ける。

## 最終コードの性能（最初の基準測定との比較）

全条件は合成メール、コマンド応答待ち20ms、3反復の中央値。単位は秒。

| 条件 | 操作 | 基準 | 最終・拡張なし | 最終・LIST-STATUS対応 |
|---|---|---:|---:|---:|
| 単一20000×2KiB | 初回 | 10.921 | 3.380 | 3.386 |
| 同上 | キャッシュ済み全件照合 | 4.688 | 1.393 | 1.396 |
| 単一2000×64KiB | 初回 | 3.764 | 2.967 | 2.861 |
| 同上 | キャッシュ済み全件照合 | 0.593 | 0.264 | 0.249 |
| 20フォルダ各500×2KiB | 初回 | 6.958 | 3.803 | 3.371 |
| 同上 | キャッシュ済み全件照合 | 3.570 | 2.171 | 1.790 |
| 同上 | 各フォルダ10追加 | 3.596 | 3.680 | 3.276 |

- 非対応同士の初回比較で単一20000通は**3.23倍（69%短縮）**、
  多数中規模は**1.83倍（45%短縮）**。LIST-STATUS対応時の多数中規模は
  基準比**2.06倍（52%短縮）**。基準版は拡張を使わないため対応の有無で処理は変わらないが、
  拡張なし同士の主比較とは区別する。
- 20000通のFETCHはヘッダ200＋本文200→20＋20。全20000本文を保持する。
  CPU中央値5.16→3.78秒。worker.stageMessages約0.97→0.80秒、
  MIME抽出約0.30秒、公開約0.61秒。複数workerの時間は重なっており加算してwallにはしない。
- 20×500通ではヘッダ100＋本文100→20＋20。
  対応サーバーでは個別STATUS20回が0回になる。
  SELECT/検証EXAMINE40回は維持し、約0.83秒を占める。

## 差分取得と残る制約

- 本文・ヘッダの少数追加最適化は維持。単一20000通＋10通では新規本文・ヘッダ各10件、
  キャッシュ20000通の本文は再取得しない。単一フォルダのCAPABILITY回数も旧版と同じ。
- ただし初回/全件が主な改善対象で、差分の実測時間が全条件で改善したわけではない。
  最初の基準に対し20000通＋10通は0.832→0.899秒、
  2000×64KiB＋10通は0.340→0.357秒、多フォルダ拡張なしは3.596→3.680秒。
  選択済み差分も20000通で0.774→0.849秒。機能確認往復を除去しても差が残るため、
  環境変動とコード差を区別するため保存済み基準EXEを最後に再測定する。
- フォルダ同士や同一フォルダの複数IMAP接続による並列取得は**未実装**。
  account単位ステージを安全に分離し、アカウント並列との総接続上限やサーバー制限を扱う
  大きな設計変更が必要なため、今回は接続を増やさず通信/解析/保存の重ね合わせを採用した。
- 64KiB本文では短縮幅が小さく、DBへのraw/検索索引の保存や
  KIMAPで解析後に再度MIME抽出する処理が残る。DB公開の原子性や最終照合を省いていない。
- 本測定は実サービス・実WAN・複雑な添付メールの保証値ではない。
  絶対的な最速や、あらゆるフォルダ構成での短縮を達成したという意味ではない。
- 通常配置`build/rel/run`はこの作業では変更していない。実メール・OS資格情報も操作していない。

## 基準版の最後の再測定

- 同じ保存済み基準EXEを測定終了後にもう一度実行し、45同期/9DBの検証が成功した。
  記録は`output/baseline-recheck`。同じEXEでも最初の基準から時間が変化していた。
  固定の「旧→新」順だけで差分の差をコードの退行と断定しない。
- 20000通＋10通は基準再測定0.895秒、新版0.899秒。
  2000×64KiB＋10通は基準再測定0.363秒、新版0.357秒。
  多フォルダ拡張なしの各10追加は基準再測定3.637秒、新版3.680秒。
  この再比較では少数追加は約±2%の範囲であり、改善を主張せず「ほぼ同程度」と評価する。
  最初の基準に対する差も上の記録から消さない。
- 大量初回は基準再測定12.224/5.173/7.317秒に対し新版3.380/2.967/3.803秒。
  初回測定と再測定の双方で大量取得改善を確認。報告の主な倍率には小さい方の
  最初の基準値を使い、環境変動による大きな倍率を選ばない。
