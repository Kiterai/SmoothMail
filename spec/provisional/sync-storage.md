# 同期保存の内部方式（暫定）

## 大量取得の内部バッチ

- 全件ヘッダ窓は最大1000件、表示・DB保存バッチは最大100件と別管理する。
- 本文転送は8MiB目標・最大1000件。未知サイズは単件、単一巨大メールと64MiB受信上限は従来通り。
- キャッシュ保存時、次の受信と前のMIME解析・保存を重ねる。消費者は各アカウント1件のみ、
  先行は1バッチだけとし、失敗・取消を含め消費者完了後にステージ破棄する。
- フォルダの最終UIDVALIDITY・件数・UIDNEXT確認と原子的公開は省略しない。
- 複数フォルダのRecent/Allでは認証後CAPABILITYを確認し、LIST-STATUS対応時に
  LIST RETURN (STATUS (UNSEEN))を利用する。欠落分は個別STATUS、明示拒否なら通常LISTへ一度だけ戻る。

性能改善のための内部方式。`behavior.md`の更新範囲とローカル編集の優先規則は変更しない。

- 同期中は新たに取得した本文・検索索引と、再利用するUID・サーバーフラグのみをアカウント別の一時テーブルへ保存する。既存本文を全コピーしない。
- 再利用確認は最大100件を1回のDBワーカー呼出し・トランザクションで処理する。本文と索引の両方が同じアカウント・フォルダ・UIDVALIDITY・UIDで存在する場合のみ再利用する。
- Recentの日時境界より古い既存メールは、検索が過大に選んでもフラグを変更しない。UIDVALIDITY内で不変のキャッシュ済みDateを利用できる。
- 公開時はフォルダ単位の1トランザクションで、取得範囲内の消失UIDを削除し、新しい本文と変更フラグのみを反映する。Recentの範囲外の行は保持する。
- 同期中に追加された保留フラグを公開前に重ねる。途中失敗・取消では未公開のステージだけを破棄する。別アカウントのステージに干渉しない。
- 永続DB形式、SQLiteの耐久性設定、本文の安全サイズ制限は変更しない。
- 小さいRecent候補、または検索拒否時は、最大1000件ずつUID FETCH FLAGSで確認する。既存UIDのヘッダと本文は再取得せず、新規UIDだけ最大100件ずつヘッダのDate・サイズを検査して本文取得計画へ追加する。UID集合の欠落、終了時のUIDVALIDITY・件数・UIDNEXT変更は引き続き失敗とする。
- 全体LISTの公開と消失フォルダの除去は、そのアカウントの最初の成功フォルダで一度だけ行う。以後は対象フォルダのみを公開する。未読数・フォルダ属性・UIDVALIDITYが不変なら永続行を書き換えない。
- 未読数の集計に後方互換の部分索引`cache_messages_unread`を追加する。テーブル／保存値／`user_version=5`は変えず、旧版からも同じデータを読み書きできる。
- Recent候補が256件を超える場合、同じSENTSINCE条件とNOT SEEN／FLAGGEDを組み合わせた標準UID SEARCHを各1回行い、2つの整列済みUID一覧からフラグを求める。個別FLAGS応答の大量解析を避ける。検索一覧の重複UID・対象外UIDは失敗とし、サーバが検索コマンドを拒否した場合だけ従来のFLAGS窓へ戻す。タイムアウト・切断・中断・不正な結果をfallbackで隠さない。
